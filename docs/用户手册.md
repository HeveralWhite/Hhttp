# Hhttp 用户手册

> **Hhttp** 是一个用 **C++17** 编写的 HTTP / WebSocket 服务器:网络层由 C++ 实现,业务逻辑交给 **QuickJS** 脚本。每条路由绑定一个 `.js` 文件,改脚本即改逻辑,无需重新编译。

本手册是 Hhttp 的完整参考:项目简介、构建、配置、JavaScript API、C++ API、运行时行为、安全与部署。
只想先把服务跑起来,请看根目录的 [README](../README.md)。

## 1. 项目简介与特性

服务器由一个可执行文件 `Hhttp.exe` 提供全部能力：读取一份 JSON 配置，
按配置打开 HTTP 与（可选）HTTPS 端口，把 URL 匹配到脚本文件并执行脚本。

### 1.1 技术栈

- **语言/标准**：C++17（CMake 项目名 `Hhttp`，版本 1.1）。
- **网络**：Boost.Asio（header-only；Windows 走 IOCP、Linux 走 epoll），
进程级 `io_context` 线程池 + 每连接 `strand`；业务层仍按“每连接一个处理线程”执行脚本。
- **TLS**：OpenSSL 3.x（PFX 与 PEM 证书、SNI 多域名、TLS 1.2 / 1.3）。
- **脚本引擎**：QuickJS（外部依赖，当前版本 2026-06-04，需提供头文件与静态库）。
- **数据库**：SQLite3（外部依赖，头文件 + 库）。
- **JSON**：单头文件库 nlohmann/json（仓库内 `third_party/nlohmann/json.hpp`）。
- **平台**：Windows x64（已验证）、Linux aarch64（已验证，openEuler 24.03）；
macOS 代码就绪但未实机验证。

### 1.2 核心特性

- **HTTP/1.1**：请求行 / 请求头 / 请求体完整解析，查询串与 Cookie 自动解码。
- **连接复用**：可开启 Keep-Alive，框架自动决策 `Connection` 头。
- **流式响应**：支持 `Transfer-Encoding: chunked`、定长流式、SSE、大文件下载。
- **WebSocket**：RFC 6455 服务端实现，自动处理分片、Ping/Pong、Close。
- **HTTPS / WSS**：基于 PFX 或 PEM 证书，按 SNI 自动选择多张证书，握手在 I/O 线程完成。
- **跨平台**：同一份源码在 Windows（IOCP）与 Linux（epoll）上构建运行，行为一致。
- **脚本化业务**：每条路由绑定 JS 脚本，改脚本即改逻辑。
- **域名路由（虚拟主机）**：默认域名表 + 域名专属表 + 通配子域。
- **脚本级文件白名单**：按脚本配置可读 / 可写目录，越界一律拒绝；
支持 `js_full_access` 显式开放全部权限。
- **SQLite3 内置支持**：脚本通过 `Sqlite` 对象读写数据库，
可按脚本限定允许的库文件（`js_sql_read_rule` / `js_sql_write_rule`）。
- **请求过滤器（中间件）**：路由前执行，可做 IP 黑名单、鉴权、限流。
- **DoS 防护**：请求行 / 请求头 / 请求体均有上限与总超时，拒绝 Slowloris。
- **访问日志**：连接、请求、响应、WebSocket 事件单独落盘，便于审计。

## 2. 快速开始

### 2.1 环境要求

- **Windows**：Windows 10 / 11（x64），MinGW-w64（GCC 13+，已在 GCC 16.2 上构建验证）或 MSVC 工具链。
- **Linux**：x86_64 或 aarch64，GCC 11+（openEuler 24.03 的 GCC 12.3 已验证）。
- **CMake** ≥ 3.16，推荐搭配 Ninja。
- **依赖**：Boost 1.74+ 头文件（Asio / System）、OpenSSL 3.x、QuickJS、SQLite3。
  版本与获取方式见 [13.2](#132-依赖与版本)。

### 2.2 构建

仓库是标准 CMake 工程：`src/` 放源码，`third_party/` 放仓库自带的 nlohmann/json。
四个外部依赖都可以用缓存变量指向本机目录；不指定（或目录里没有头文件）时自动回退到
`find_package(Boost/OpenSSL/SQLite3)` 与 `find_path(quickjs.h)`：

**外部依赖的定位方式**

| 缓存变量 | 目录内容 | 回退方式 |
| --- | --- | --- |
| `HHTTP_BOOST_DIR` | Boost 源码根（含 `boost/asio.hpp`） | `find_package(Boost)` |
| `HHTTP_OPENSSL_DIR` | `include/` + `lib/`（优先链 `libssl.a` / `libcrypto.a`） | `find_package(OpenSSL)` |
| `HHTTP_QUICKJS_DIR` | `include/quickjs.h` + `lib/libquickjs.a` | `find_path` / `find_library` |
| `HHTTP_SQLITE3_DIR` | `include/sqlite3.h` + `lib/libsqlite3.a` | `find_package(SQLite3)` |

Linux / macOS（依赖已装在系统里）：

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

Windows（MinGW-w64，依赖放在自定义目录）：

```powershell
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release `
  -DHHTTP_BOOST_DIR=A:/libs/boost_1_92_0 `
  -DHHTTP_OPENSSL_DIR=A:/libs/openssl `
  -DHHTTP_QUICKJS_DIR=A:/libs/quickjs `
  -DHHTTP_SQLITE3_DIR=A:/libs/sqlite3
cmake --build build
```

- 产物为 `build/Hhttp.exe`（Linux 为 `build/Hhttp`），默认 **Release**（`-O2 -DNDEBUG`）。
  需要调试构建时用 `-DCMAKE_BUILD_TYPE=Debug`；`CMakePresets.json` 里另有
  `release` / `debug` / `relwithdebinfo` 三个预设（`cmake --preset release`，需要 CMake ≥ 3.23）。
- MinGW 下默认 `-static` 链接 OpenSSL / QuickJS / SQLite3 与 MinGW 运行时，
  产物是单个 exe，不需要附带 DLL。
- **MSVC**：CMake 已按编译器区分平台库（`ws2_32` 等），但 QuickJS / SQLite3 / OpenSSL
  需要用 MSVC 编译的版本，并通过 `HHTTP_*_DIR` 指过去，详见 13.3。

### 2.4 第一个脚本

仓库自带的 `scripts/hello.js` 就是第一个脚本：`/` 返回 HTML 页面，
`/api/time` 返回 JSON，`/api/echo` 回显请求。核心代码只有几行：

```js
const req = HTTP.get;   // 当前请求
const res = HTTP.send;  // 待发送的响应

res.status(200);
res.header("X-Powered-By", "Hhttp");
res.html("<h1>Hello Hhttp</h1>");
res.send();             // 必须显式调用才会发送
```

完整写法见 [scripts/hello.js](../scripts/hello.js)。脚本每次请求都会重新加载，改完立即生效。

## 4. 命令行参数

**Hhttp.exe 支持的参数**

| 参数 | 含义 | 默认值 |
| --- | --- | --- |
| `--config <path>`、`-c <path>` | 配置文件路径 | `config.json` |
| `--dir <path>` | 脚本目录（`js_path` 与文件规则的基准） | 配置里的 `base_msg.script_dir`，否则 `scripts` |
| `--file-max-size <bytes>` | 脚本单次读取文件的上限 | `8388608`（8 MiB） |
| `--js-memory-limit <bytes>` | 业务脚本内存上限，等价于 `base_msg.js_memory_limit` | `67108864`（64 MiB） |
| `--js-security-memory-limit <bytes>` | 安全检测脚本内存上限，等价于 `base_msg.js_security_memory_limit` | `67108864`（64 MiB） |
| `--js-global-memory-limit <bytes>` | 全局数据脚本内存上限，等价于 `base_msg.js_global_memory_limit` | `134217728`（128 MiB） |
| `--help`、`-h` | 打印用法并退出 | — |

**优先级**：命令行 > 配置文件。即 `--dir` 覆盖 `base_msg.script_dir`，
`--file-max-size` 覆盖 `base_msg.file_max_size`；
`--js-memory-limit` / `--js-security-memory-limit` /
`--js-global-memory-limit` 分别覆盖 `base_msg.js_memory_limit` /
`js_security_memory_limit` / `js_global_memory_limit`。
内存数值一律按**字节**解释，`0` 表示不限制。

**相对路径回退规则**（对 `--config` 与 `--dir` 都生效）：

1. 先在**当前工作目录**下查找；
2. 找不到则在 **exe 所在目录**下查找；
3. 再找不到则在 **exe 所在目录的上一级**下查找。

因此直接在 `build/` 里运行 `Hhttp.exe`，也能自动找到源码根目录下的
`config.json` 与 `scripts/`。

未知参数会打印错误并返回码 1；配置错误、端口非法、证书加载失败同样返回 1。

### 5.2 base_msg

**base_msg 字段**

| 字段 | 类型 | 必需 | 说明 |
| --- | --- | --- | --- |
| `HTTP_port` | 整数 / 数字字符串 | 与 HTTPS_port 至少一个非 0 | 明文 HTTP 监听端口；`0` 表示不监听。 |
| `HTTPS_port` | 整数 / 数字字符串 | 否 | HTTPS/WSS 监听端口；`0` 表示不监听。与 `HTTP_port` 不能相同。 |
| `pfx_path` | 字符串 | HTTPS 必需（或用 certificates） | PFX/P12 证书路径。相对路径以**配置文件所在目录**为基准；   为空且没写 `certificates` 时禁用 HTTPS。 |
| `pfx_password` | 字符串 | 否 | PFX 密码，无密码留空。 |
| `certificates` | 数组 | 否 | 可选。多证书写法，用于**一个 HTTPS 端口服务多个域名**：   `[{"pfx_path": "a.pfx", "pfx_password": "..."}, ...]`。   写了它时忽略 `pfx_path` / `pfx_password`；第一张是默认证书，   其余按客户端 TLS **SNI** 里的域名自动选用（支持 CN 与 SAN 里的 DNS 名、   `*.example.com` 通配）。路由里出现的域名没有对应证书时，启动日志会告警。 |
| `colorful_log` | 布尔 | 否 | 可选。是否输出彩色日志（ANSI 转义序列），默认 `true`。   终端 / 平台不支持 ANSI 时设为 `false`，控制台只输出纯文本、不写任何转义序列；   只影响控制台，落盘文件日志本来就不含转义序列。 |
| `script_dir` | 字符串 | 否 | 可选。脚本目录，等价于 `--dir`（命令行优先）。 |
| `file_max_size` | 整数（字节） | 否 | 可选。脚本单次读取上限，等价于 `--file-max-size`。默认 8 MiB。 |
| `js_memory_limit` | 整数（字节） | 否 | 可选。业务脚本内存上限，等价于 `--js-memory-limit`；`0` 表示不限制。默认 64 MiB。 |
| `js_security_memory_limit` | 整数（字节） | 否 | 可选。安全检测脚本内存上限，等价于 `--js-security-memory-limit`；`0` 表示不限制。默认 64 MiB。 |
| `js_global_memory_limit` | 整数（字节） | 否 | 可选。全局数据脚本内存上限，等价于 `--js-global-memory-limit`；`0` 表示不限制。默认 128 MiB。启动日志会打印三个生效值，便于确认。 |
| `js_exec_timeout_ms` | 整数（毫秒） | 否 | 可选。脚本单次执行超时；`0` 或不写表示不限制。超时后脚本抛   `InternalError: interrupted`（HTTP 回 500，WebSocket 以 1011 关闭）。 |
| `websocket_recv_timeout_ms` | 整数（毫秒） | 否 | 可选。`ws.recv()` 不传参数时的缺省超时；`0` 或不写表示一直阻塞。 |
| `js_security_script` | 字符串 / 对象 | 否 | 可选。安全检测脚本（相对 `--dir`）；需定义 `check(req)`。   不写表示不启用。检测脚本异常/超时一律按 **500** 处理（fail-closed）。      字符串写法只给脚本路径，**没有任何文件 / SQL 权限**；   对象写法与 roter 处理器字段一致（`js_path` / `js_read_rule` /   `js_write_rule` / `js_sql_read_rule` / `js_sql_write_rule` /   `js_full_access`），可单独授予 `File` 与 `Sqlite` 权限。 |
| `js_global_script` | 字符串 / 对象 | 否 | 可选。全局数据脚本（相对 `--dir`）；启动时执行一次并常驻，   网页脚本通过 `Global.call(name, args)` 同步调用其函数。不写表示不启用。      字符串写法沿用旧版本行为（完全文件 / SQL 权限）；对象写法与 roter 处理器字段一致，   可按 `js_read_rule` / `js_write_rule` / `js_sql_read_rule` /   `js_sql_write_rule` / `js_full_access` 精确配置权限。 |

**js_security_script / js_global_script 的对象写法**（与 roter 处理器完全一致）：

```
"js_security_script": {
  "js_path": "security.js",
  "js_read_rule": "data",
  "js_write_rule": "data",
  "js_sql_read_rule": "data/app.db",
  "js_sql_write_rule": "data/app.db",
  "js_full_access": false
},
"js_global_script": {
  "js_path": "global.js",
  "js_read_rule": "data",
  "js_write_rule": "data",
  "js_sql_read_rule": "data/app.db",
  "js_sql_write_rule": "data/app.db",
  "js_full_access": false
}
```

字段含义见 [5.3 roter 与 undefine_roter](#53-roter-与-undefine_roter)；
权限规则本身与业务脚本共用同一套（见 5.5 / 5.6）。脚本目录之外的脚本只能靠
`js_full_access` 生效。对象写法下 `js_path` 留空表示不启用该脚本。

**js_security_script 的 check(req)**：`req` 只读，提供
`method` / `url` / `rawUrl` / `version` /
`header(name)` / `ip` / `peer` / `cookies()` /
`isHttps()` / `scheme()` / `tlsProtocol()`。
返回值：`true` 或 `undefined` 放行；`false` 返回 403；
数字按该状态码拒绝；`-1` 表示**静默断开**——不发送状态行 / 响应头 / 正文，
直接关闭连接；`{ allow, status, message, headers }` 精确控制响应，
其中 `{ close: true }` 等价于 `-1`。
按对象写法授予权限后，检测脚本同样可以使用 `File` / `Sqlite`
（但没有 `HTTP.send`，不能自行发送响应）。

**内存上限**：三个 `js_*_memory_limit` 直接交给 QuickJS 的
`JS_SetMemoryLimit`，超出时脚本的内存申请失败并抛出异常，按各入口的 fail-closed 规则处理
（HTTP 回 500、安全脚本拒绝请求、全局脚本启动失败直接退出）。负数视为非法配置，
程序会带着明确错误信息退出。

**校验行为**：

- `HTTP_port` 与 `HTTPS_port` 都为 0 → 报错退出（无监听端口）。
- 端口不在 1–65535 范围，或两者相等 → 报错退出。
- 设置了 `HTTPS_port` 但没有任何证书（`pfx_path` 与 `certificates` 都为空）→ 告警并**禁用 HTTPS**。
- 平台不支持 TLS（`TLS::available()` 为假）或上下文创建失败 → 告警禁用 / 报错退出。

### 5.2.1 多域名 HTTPS：certificates 与 SNI

一张证书只对它证书里的域名（CN / SAN）有效。同一个 HTTPS 端口要服务多个域名时，
用 `base_msg.certificates` 给每个域名配一张证书（PFX 或 PEM 均可）：

```
"base_msg": {
  "HTTP_port": 80,
  "HTTPS_port": 443,
  "certificates": [
    { "pfx_path": "certs/a.example.com.pfx", "pfx_password": "***" },
    { "pfx_path": "certs/b.example.com.pfx", "pfx_password": "***" }
  ]
}
```

PEM 是 OpenSSL 原生格式，证书链与私钥分两个文件：

```
"certificates": [
  { "cert_file": "certs/a.example.com.pem", "key_file": "certs/a.example.com.key" },
  { "cert_file": "certs/b.example.com.pem", "key_file": "certs/b.example.com.key" }
]
```

- 证书来源：PFX（`pfx_path` / `pfx_password`）或 PEM（`cert_file` / `key_file`）；
`cert_thumbprint` / `cert_subject`（Windows 证书存储）已不再支持。
- 列表里的**第一张是默认证书**：客户端没有发 SNI、或没有匹配到证书时使用它。
- 其余证书按 ClientHello 里的 **SNI 域名**自动选择；匹配依据是证书的 CN 与 SAN 里的
DNS 名，支持 `*.example.com` 通配（只匹配一级，不匹配 `a.b.example.com`）。
- 写了 `certificates` 时忽略 `pfx_path` / `pfx_password`；
只有一个域名时继续用它们即可，行为不变。
- 启动日志会打印加载的证书数量；路由里出现、但没有任何证书覆盖的域名会输出告警，
提示在 `certificates` 里补一张对应证书。
- HTTPS 与 WSS 共用这套证书选择逻辑。

### 5.3 roter 与 undefine_roter

`roter` 是一个**数组**，每个元素是一个对象，对象里可以写多条路由：
`"域名/路径"` → `{ "http": {...}, "websocket": {...} }`。
键名也接受拼写 `router`（两者存在时优先 `roter`）。

每个处理器对象（`http` / `websocket`）包含以下字段：

**处理器字段**

| 字段 | 说明 | 留空时 |
| --- | --- | --- |
| `js_path` | 脚本路径，相对脚本目录（也可写绝对路径）。 | 该类型不处理：请求转交 `undefine_roter` 里对应类型的处理器；未配置兜底时 HTTP / WebSocket 均回 404。 |
| `js_read_rule` | 允许读取的目录列表，`,` 或 `;` 分隔，相对脚本目录。 | 禁止读（`File.read` 等全部拒绝）。 |
| `js_write_rule` | 允许写入的目录列表，规则同上。 | 禁止写（`File.write` 等全部拒绝）。 |
| `js_sql_read_rule` | 允许**只读**打开的数据库列表，`,` 或 `;` 分隔；相对路径以脚本目录为基准，也可写绝对路径，支持 `*` / `**` 通配。 | 禁止只读打开（全局对象 `Sqlite` 不会安装）。 |
| `js_sql_write_rule` | 允许**读写**打开的数据库列表，规则同上（写权限包含读权限）。 | 禁止读写打开，只读仍可用。 |
| `js_full_access` | 布尔值。为 `true` 时该脚本可访问**整个文件系统**（含 `C:/...` 这样的绝对路径与 `..`）和**任意** sqlite 数据库文件，上面四个规则字段被忽略。 | `false`：完全按上述规限工作。 |

`undefine_roter` 是**没有匹配到可处理该请求类型的路由**时使用的兜底处理器，
结构同上（只有 `http` / `websocket` 两个成员）。键名也接受
`undefined_router`。未配置时框架默认返回 404。

兜底处理器**按请求类型**调用：普通 HTTP 请求走它的 `http` 脚本，
WebSocket 请求走它的 `websocket` 脚本；某一类型没写脚本时该类型仍按 404 处理。
“路径完全没命中”和“路径命中、但该路径只配置了另一种请求类型”都算未匹配到路由，都会落到这里。

**实现细节**：框架的域名表一旦命中就不再回退默认表，因此 `main.cpp`
会把同一个兜底处理器同时安装到默认表与**每个**已注册域名上。
没有写任何 `js_path` 的路由会被忽略并打一条告警。

### 5.4 路由键写法与匹配规则

**路由键的三种形态**

| 写法 | 含义 | 示例 |
| --- | --- | --- |
| `"域名/路径"` | 只对指定域名（虚拟主机）生效。 | `"localhost/index"`、`"api.example.com/v1/"` |
| `"/路径"` | 写入**默认域名表**，对任意 Host 生效（仅当没有同名域名专属表时）。 | `"/index"`、`"/"` |
| `"*.域名/路径"` | 通配子域，匹配任意一级或多级子域。 | `"*.example.com/api/"` |

**匹配规则汇总**：

- 一条路由 = **路径 + 请求类型**：同一路径可以同时配置 `http` 与
`websocket`（写在同一个对象里，或拆成两条路由），两者**互不覆盖**。
- 域名匹配**大小写不敏感**，可写端口（端口会被忽略），结尾的点会被去掉。
- 域名表查找顺序：**精确域名** → **通配子域** → 若都没命中才用**默认表**。
- 多个通配子域同时命中时，取**后缀最长（最具体）**的一条，与配置书写顺序无关
（例如 `*.wild.test` 优先于 `*.test`）。
- 路径以 `/` 结尾（含 `/` 本身）表示**前缀匹配**，其余为**精确匹配**。
- 精确匹配与前缀匹配同时命中时，取**更精确**的那一条（精确优先，前缀取最长）。
- 路径命中后**再按请求类型**取处理器：WebSocket 请求优先用同路径的
`websocket` 处理器，其次才看通用处理器；该路径没有当前类型的处理器时交给
`undefine_roter`，都没有则 404。
- 同一路径、同一类型**重复配置**时只有最后一次生效，启动日志会输出
“... router ... replaced by a later registration” 告警。
- 路由键结尾写 `*` 或 `**` 会被等价转换为前缀匹配（配置解析时去掉结尾星号）。
- 只写域名不写路径（如 `"example.com"`）等价于路径 `/`。

### 5.5 脚本文件访问规则

脚本的文件能力**默认完全关闭**：只有在配置里给出 `js_read_rule` /
`js_write_rule`，对应脚本才拥有该方向的权限。规则模型是
“**脚本 → 允许目录**”，进程级生效：

- 规则的键是**脚本相对脚本目录的路径**（统一 `/`、转小写）。脚本位于脚本目录之外时，
该脚本的文件访问一律拒绝，并打告警。
- 同一脚本被多条路由引用时，目录列表取**并集**。
- 规则对**所有脚本种类**生效：路由脚本、安全检测脚本
（`base_msg.js_security_script`）与全局数据脚本
（`base_msg.js_global_script`）都用同一套目录规则，
后两者把入口写成对象即可授予权限（见 5.2）。
- 脚本传入的路径一律按“**相对脚本目录**”解释；`..`、绝对路径、盘符路径直接拒绝。
- 解析时消解符号链接，再确认目标仍落在允许目录内。
- 读与写两个方向**互相独立**：`read`/`exists`/`size`/`list`
只看读目录；`write`/`append`/`remove`/`mkdir` 只看写目录。
- 单次读取大小受 `max_read_size`（`--file-max-size`）限制，`0` 表示不限制。

目录列表解析细节：`,` 与 `;` 都是分隔符，空项与首尾空白被忽略。

### 5.6 脚本 SQL 访问规则与完全访问

SQLite 能力同样**默认关闭**：只有配置了 `js_sql_read_rule` 或
`js_sql_write_rule` 的脚本，全局对象 `Sqlite` 才会被安装；
两个字段都留空时全局对象不存在，脚本里的 `Sqlite` 是 `undefined`。
安全检测脚本与全局数据脚本同样适用：把 `base_msg.js_security_script` /
`base_msg.js_global_script` 写成对象并给出 `js_sql_*` 即可。

- 数据库路径按“相对脚本目录”解释；也可写绝对路径（如 `C:/data/app.db`），
但必须命中规则里的绝对写法。
- 路径会先消解 `..` 与符号链接，再与规则逐一比对，因此
`data/*.db` 不会放行 `data/../secret.db`。
- 命中 `js_sql_write_rule` 即可读写打开；只命中 `js_sql_read_rule`
时只能 `{readonly: true}` 打开，写语句会抛异常。
- 默认使用 SQLite 的读写模式打开（文件不存在则创建）；
传 `{readonly: true}` 则为只读。

**js_full_access** 是显式开启的高危开关：开启后该脚本的
`File.*` 可读写任意路径（包括盘符绝对路径与 `..`），
`Sqlite.open` 不受 `js_sql_*` 限制，且即使脚本位于脚本目录之外也能生效。
只应对完全可信的脚本开启。

```
"http": {
    "js_path": "tools/db_admin.js",
    "js_read_rule": "",
    "js_write_rule": "",
    "js_sql_read_rule": "",
    "js_sql_write_rule": "",
    "js_full_access": true
}
```

## 6. JavaScript 脚本 API

### 6.1 运行模型与约束

- **每次请求一个隔离环境**：框架为每次 HTTP 请求新建一个 `JSRuntime` /
`JSContext`，脚本之间不共享全局状态。
- **构造即执行**：`JS_HTTP` / `JS_WS` 在构造时加载并执行脚本。
- **必须发送响应**：HTTP 脚本若抛异常或未调用 `HTTP.send.send()`，
框架返回 **500**；异常堆栈同时写入日志。
- **WebSocket**：脚本返回（或抛异常）后框架关闭连接；抛异常时以
**1011** 关闭并记日志。
- **执行线程**：脚本运行在**该连接的专属工作线程**中，
可使用阻塞式 `ws.recv()` 写“收一条、处理、再收一条”的循环。

### 6.2 HTTP.get（请求对象）

全局对象 `HTTP` 上提供 `HTTP.get`，映射当前请求。

**HTTP.get 成员**

| 成员 | 返回 | 说明 |
| --- | --- | --- |
| `method()` | string | 请求方法，如 `GET`、`POST`。 |
| `url()` | string | 解码后的路径（不含查询串）。 |
| `rawUrl()` | string | 原始请求目标（未解码，含查询串）。 |
| `version()` | string | HTTP 版本，如 `HTTP/1.1`。 |
| `query()` | object | 查询参数键值对（已 URL 解码）。 |
| `headers()` | object | 全部请求头，键名统一小写。 |
| `header(name)` | string | 取单个请求头（大小写不敏感），不存在返回空串。 |
| `cookies()` | object | 解析后的 Cookie 键值对。 |
| `cookie(name)` | string | 取单个 Cookie（名字区分大小写）。 |
| `body()` | string | 请求体文本。 |
| `bodyBytes()` | Uint8Array | 请求体原始字节（二进制上传用）。 |
| `peer()` | string | 对端 `IP:端口`。 |
| `ip()` | string | 对端 IP。 |
| `isHttps()` | boolean | 当前连接是否 HTTPS（启用了 TLS）。WSS 连接同样返回 `true`。 |
| `scheme()` | string | 当前请求的 URL scheme：`"https"` 或 `"http"`。 |
| `tlsProtocol()` | string | 协商出的 TLS 协议版本（如 `"TLS 1.3"`）；非 TLS 连接返回空串。 |

监听端口是否走了 TLS 由连接本身决定，所以同一个处理脚本可以同时服务 HTTP 与 HTTPS 端口：
用 `HTTP.get.isHttps()` / `scheme()` 即可区分，
例如回写 `Secure` Cookie、生成绝对 URL、或对明文连接强制跳转 HTTPS。

### 6.3 HTTP.send（响应对象）

全局对象 `HTTP` 上提供 `HTTP.send`，代表待发送的响应。
设置类方法返回自身或设置值，最终必须调用 `send()`。

**HTTP.send 成员**

| 成员 | 说明 |
| --- | --- |
| `status(code[, text])` | 设置状态码，可选自定义原因短语；不传参返回当前状态码。 |
| `header(name[, value])` | 有 `value` 时设置响应头；只有一个参数时返回该响应头的当前值。 |
| `removeHeader(name)` | 删除响应头，返回是否删除成功。 |
| `body(text)` | 设置 / 读取响应体字符串（不改变 Content-Type）。 |
| `text(str[, status])` | 以 `text/plain; charset=utf-8` 设置响应体。 |
| `html(str[, status])` | 以 `text/html; charset=utf-8` 设置响应体。 |
| `json(value[, status])` | 以 `application/json` 设置响应体；对象自动序列化，字符串按原样使用。 |
| `binary(data[, status])` | 以二进制设置响应体（字符串 / Uint8Array / ArrayBuffer），默认 `application/octet-stream`，已显式设置 Content-Type 时尊重脚本选择。 |
| `chunkBinary(data)` | 流式发送一段二进制数据（自动先发响应头），返回连接是否仍可用。 |
| `file(path[, contentType])` | 直接把文件内容作为响应发送：受文件读规则约束，自动补 `Content-Length` 走定长流式，**大文件不整块读入内存**；省略类型时按扩展名猜测。 |
| `redirect(location[, status])` | 设置 `Location` 头，默认 302。 |
| `cookie(cookieOrObject)` | 追加一条 `Set-Cookie`（可用 `new Cookie(...)` 或普通对象）。 |
| `keepAlive(enable)` | 显式指定是否复用连接（默认由框架自动决策）。 |
| `beginStream()` | 开始流式响应（等价于先发响应头）。 |
| `chunk(data)` | 发送一段文本/字节流数据；分块模式下自动加长度封装。 |
| `endStream()` | 结束流式响应（分块模式补发结束块），并输出响应访问日志。 |
| `fake_close()` | 关断非法请求：不发送状态行 / 响应头 / 正文，直接关闭连接；之后框架也不再补发任何响应（包括 500 兜底）。 |
| `send()` | 发送响应（一次性发送时框架自动补 `Content-Length`）。 |
| `sent()` | 响应是否已经开始发送。 |

**流式响应三种定界方式**（由框架自动选择，也可显式干预）：

1. 脚本给出 `Content-Length` → 定长流式（`res.file` 即走这条）；
2. 未给长度且客户端为 HTTP/1.1 → `Transfer-Encoding: chunked`；
3. 客户端不支持分块（如 HTTP/1.0）→ 强制 `Connection: close`，用关闭连接定界。

### 6.4 File（文件读写）

全局对象 `File` 提供受限的文件操作，路径按“相对脚本目录”解释，
必须落在该脚本被允许的目录内（见 [5.5](#55-脚本文件访问规则)）。
`data` 参数可以是字符串、`Uint8Array` 或 `ArrayBuffer`；
`read()` 返回 `Uint8Array`。

**范围读取**：`read(path, start, end)` / `readText(path, start, end)`
按 `[start, end)` 截取，单位是**字节**；`start` 缺省 0，
`end` 缺省为文件末尾。负数表示从文件末尾倒数，越界自动截断到 `[0, size]`，
与 Python 切片一致。例如读取第 200~300 字节（下标从 0 开始、`end` 不含）：
`File.read("data/blob.bin", 199, 299)`。
**max_read_size 只校验实际读取的区间**，因此超出上限的大文件也能分块读取。
同时给出 `start` 与 `end` 且 `end < start` 时抛 `RangeError`，不会静默返回空字节。

**按行读取**：`File.getline(path[, index])` 读取第 `index` 行
（从 0 开始，缺省 `0`），返回值**不含**行尾的 `\r\n` / `\n`。
空行返回空串 `""`；行号超出文件行数（或文件为空）返回 `null`，
所以判断“是否还有下一行”要看返回值是不是 `null`：

```js
for (let i = 0; ; ++i) {
  const line = File.getline("data/log.txt", i);
  if (line === null) break;   // 没有第 i 行了
  if (line === "") continue;  // 空行不算结束
  log(i, line);
}
```

行号会先按 `Number` 截断取整（`NaN` 视作 0、`1.9` 当作 1、`true` 当作 1），
截断后为负数抛 `RangeError`；单行的字节数超过 `max_read_size` 抛错
（文件超出上限时边读边校验，不会先为超长行分配内存）。
实现逐行跳到目标行，内存只占一行，读大文件末尾的行不会把整个文件读进来；
但每次调用都是从文件头跳行（`O(index)`），连续逐行遍历请自行缓存结果。
读权限、路径规则与限流都跟 `File.read` 完全一致。

**File 成员**

| 成员 | 方向 | 说明 |
| --- | --- | --- |
| `read(path[, start[, end]])` | 读 | 读取文件原始字节，返回 `Uint8Array`；给出 `start` / `end` 时只读该区间。 |
| `readText(path[, start[, end]])` | 读 | 读取文件文本；区间语义与 `read` 相同。 |
| `getline(path[, index])` | 读 | 读取第 `index` 行（从 0 开始，缺省 0），返回不含行尾换行符的字符串；空行返回 `""`，行号越界或文件为空返回 `null`。 |
| `write(path, data)` | 写 | 覆盖写入。 |
| `append(path, data)` | 写 | 追加写入。 |
| `exists(path)` | 读 | 文件是否存在。 |
| `size(path)` | 读 | 文件字节数。 |
| `list([path])` | 读 | 列出目录内容，返回字符串数组；不传参时列出第一条读目录。 |
| `remove(path)` | 写 | 删除文件。 |
| `mkdir(path)` | 写 | 创建目录。 |
| `root()` | — | 脚本目录（规则基准）。 |
| `roots()` | — | 当前脚本可用的读/写目录列表。 |
| `canRead()` | — | 当前脚本是否有读权限。 |
| `canWrite()` | — | 当前脚本是否有写权限。 |

### 6.5 Sqlite（SQLite3）

**Sqlite 成员**

| 成员 | 说明 |
| --- | --- |
| `Sqlite.open(path[, {readonly: true}])` | 打开数据库，返回数据库对象；未授权、路径越界或文件无法打开时抛异常。 |
| `db.exec(sql)` | 执行一段（可含多条语句）SQL，返回 `true`。 |
| `db.run(sql, ...params)` | 执行写语句，返回 `{changes, lastInsertRowid}`。 |

```js
const db = Sqlite.open("data/app.db");

db.run("INSERT INTO note (body) VALUES (?)", "hello");
const rows = db.query("SELECT * FROM note");  // rows.columns === ["id", "body"]
db.close();
```

### 6.9 完整脚本示例

#### HTTP：按路径分发 + 读文件 + JSON

```js
// scripts/index.js
const req = HTTP.get;
const res = HTTP.send;

const path = req.url();
log(req.method() + " " + path);

if (path === "/api/time") {
    res.json({ ok: true, now: Date.now() }, 200);
    res.send();
} else if (path === "/api/echo" && req.method() === "POST") {
    const data = req.body();
    res.header("X-Echo-Len", String(data.length));
    res.text("received " + data.length + " bytes");
    res.send();
} else {
    // 读规则如果是 "html,data"，则 "html/index.html" 在允许范围内
    if (File.exists("html/index.html")) {
        res.header("Content-Type", "text/html; charset=utf-8");
        res.body(File.readText("html/index.html"));
    } else {
        res.status(404);
        res.text("not found");
    }
    res.send();
}
```

#### HTTP：流式（Server-Sent Events 风格）

```js
// scripts/stream.js
const res = HTTP.send;
res.header("Content-Type", "text/event-stream; charset=utf-8");
res.header("Cache-Control", "no-cache");
res.beginStream();

for (let i = 0; i < 10; ++i) {
    if (!res.chunk("data: tick " + i + "\n\n")) break;
    // 真实场景在此可 sleep / 等待队列数据
}
res.endStream();
```

#### WebSocket：回显聊天室

```js
// scripts/chat.js
ws.send("welcome, " + ws.peer());

while (ws.valid()) {
    const msg = ws.recv(1000);        // 1 秒超时
    if (msg === undefined) {
        continue;                     // 空闲：这里可做定时推送
    }
    if (msg === null) {
        break;                        // 对端关闭
    }
    if (ws.lastBinary()) {
        ws.sendBinary(msg);           // 二进制原样回送
    } else {
        ws.send("echo: " + msg);
    }
}
```

### 6.10 Global（全局数据脚本）

配置 `base_msg.js_global_script` 后，框架在启动监听端口之前先执行一次本脚本；
进程存活期间它一直驻留，网页脚本通过全局对象 `Global` 与它交互。
未配置全局脚本时 `Global` 不存在（脚本里访问会得到 `undefined`）。

**Global 成员（仅在配置了全局脚本时存在）**

| 成员 | 说明 |
| --- | --- |
| `Global.get(key)` | 读全局数据（返回反序列化后的值；不存在返回 `undefined`）。 |
| `Global.set(key, value)` | 写全局数据（值必须可 JSON 序列化）。 |
| `Global.del(key)` | 删除一条全局数据。 |
| `Global.has(key)` | 是否存在该键。 |
| `Global.keys()` | 全部键名（数组）。 |
| `Global.call(name[, args])` | 同步调用全局脚本里挂到 `globalThis` 的函数：**网页脚本会阻塞到本次调用返回**；`args` 为数组时按数组展开，否则包装成单元素数组（也支持 `Global.call(name, a, b)` 传多个参数）；返回值按 JSON 反序列化；函数不存在或抛异常时脚本收到异常。 |

**使用约定**：

- 参数与返回值都走 JSON 往返，不能传函数、`undefined` 或循环引用。
- `Global.get` / `set` / `del` 访问的是进程级内存表；
    `Global.call` 调用的是全局脚本里的函数，两套机制互相独立。
- 全局脚本的文件 / SQL 权限由 `base_msg.js_global_script` 配置，
    也没有 `HTTP` / `ws` 对象。把 `js_global_script`
    写成对象（字段与 roter 处理器一致，见 5.2），即可按 `js_read_rule` /
    `js_write_rule` / `js_sql_read_rule` / `js_sql_write_rule` /
    `js_full_access` 授予 `File` / `Sqlite` 权限
    （不写规则 = 默认不开放）；字符串写法是旧版本行为，等价于完全文件 / SQL 访问。
- `Global.call` 由全局脚本所在线程串行执行，单次调用耗时过长会拖慢所有调用方；
    配合 `js_exec_timeout_ms` 可避免无限阻塞。

```js
// 全局脚本（base_msg.js_global_script）
globalThis.add = function (a, b) { return Number(a) + Number(b); };

// 网页脚本
const sum = Global.call("add", [1, 2]);   // 3
Global.set("visit_count", (Global.get("visit_count") || 0) + 1);
```

### 7.1 TCP 层（命名空间 TCP）

#### TCP::Base_Link

一条 TCP 连接；同一对象既可承载明文，也可承载已握手的 TLS 连接（自动加解密）。

**Base_Link 主要接口**

| 接口 | 说明 |
| --- | --- |
| `bool valid() const` | 连接是否有效。 |
| `void Close()` | 立即关闭连接（最高优先级，可从其它线程调用）。 |
| `std::string get_ip() const` | 对端 IP。 |
| `std::string get_peer() const` | 对端 `IP:端口`，日志中区分同 IP 不同连接。 |
| `bool is_tls() const` | 是否为 TLS 加密连接。 |
| `SOCKET native_handle() const` | 底层套接字句柄。 |
| `void upgrade_tls(std::shared_ptr<TLS::Connection>)` | 把明文连接升级为 TLS（必须在任何收发之前）。 |
| `void Send_str(const std::string&)` | 发送字符串（发送不阻塞接收）。 |
| `void Send_sb(const std::vector<char>&)` | 发送字节。 |

| `ReadStatus Read_until(const std::string& end, int timeout_ms, size_t max_bytes, std::string& out)` | 有界读取，返回 `Ok` / `Timeout` / `Closed` / `Overflow`；多余字节留在内部缓存不丢弃。 |
| `void Shutdown_send()` | 半关闭写方向（发送 FIN，仍可读）。 |
| `void Drain(int timeout_ms, size_t max_bytes = 256 * 1024)` | 丢弃对端剩余输入，避免未读数据触发 RST 冲掉已发响应。 |

#### TCP::Server

- `Server(SOCKET socket, sockaddr_in server)`：接管一个已 `bind` 的套接字。
- `Base_Link get_link()`：阻塞等待新连接；服务器关闭时返回无效对象。
- `bool valid() const`：是否处于监听状态。
- `void Close()`：关闭监听，并立即唤醒阻塞在 `get_link()` 的线程（线程安全）。
- 不可拷贝、不可移动。

### 7.2 HTTP 请求与响应

#### HTTP::Header_get（请求）

**Header_get 字段与方法**

| 成员 | 说明 |
| --- | --- |
| `method` / `url` / `raw_url` / `version` | 方法、解码路径、原始目标、版本。 |
| `query` | `map<string, string>`，查询参数（已解码）。 |
| `headers` | 请求头，键名**统一小写**。 |
| `cookies` | 解析后的 Cookie 键值对。 |
| `body` | 请求体。 |
| `int error() const` | 0 正常；否则为应回应的状态码（400/408/413/414/431）。 |
| `std::string get(key, def = "") const` | 取请求头（大小写不敏感）。 |
| `bool has(key) const` | 是否存在该请求头。 |
| `std::string cookie(name, def = "") const` | 取 Cookie（名字区分大小写）。 |
| `bool has_cookie(name) const` | 是否存在该 Cookie。 |
| `bool is_websocket() const` | 是否为 WebSocket 升级请求。 |
| `bool keep_alive() const` | 客户端是否希望保持长连接。 |

构造方式：`Header_get(TCP::Base_Link& link, int timeout_ms = 0, const Limits& limits = Limits{})`。
`timeout_ms` 是整个请求（行 + 头 + 体）的**总超时**，0 表示无限等待（不推荐）。

#### HTTP::Header_send（响应）

字段：

- `status`（默认 200）、`status_text`（空则自动生成）、`version`（默认 `HTTP/1.1`）。
- `headers`（`map<string, string>`）、`body`、`set_cookies`（多条 Set-Cookie）。
- `keep_alive` / `keep_alive_auto`（默认自动决策）。
- `streaming`（首次调用 `send_head`/`send_chunk` 时自动置真）、`use_chunked`。
- `head_sent_` / `streamed_bytes_`：流式内部状态。

**Header_send 方法**

| 方法 | 说明 |
| --- | --- |
| `set_header(key, value)` | 设置响应头。 |
| `add_cookie(const Cookie&)` / `add_cookie(const std::string&)` | 追加 `Set-Cookie`（结构体或原始值）。 |
| `delete_cookie(name, path = "/")` | 输出 `Max-Age=0` 与过期时间以删除 Cookie。 |
| `serialize()` / `serialize_head()` | 序列化整份报文 / 只序列化头部（流式时自动决定定界方式）。 |
| `send(link)` | 发送：非流式一次性发出；流式等价于 `send_head` + 首段 + `end_stream`。 |
| `is_chunked()` / `is_close_delimited()` | 是否分块 / 是否以关闭连接定界。 |
| `head_sent()` / `streamed_bytes()` | 头部是否已发出 / 已发出的流式字节数。 |
| `has_header(key)` | 是否存在该响应头（大小写不敏感）。 |
| `is_head_request()` / `body_suppressed()` | 是否为 HEAD 请求 / 是否应抑制响应体（HEAD、1xx、204、304）。 |
| `will_reuse_connection()` | 响应头是否会声明连接可复用（同时影响日志）。 |
| `send_head(link)` | 发送响应头，返回连接是否仍可用；重复调用不会重复发送。 |
| `send_chunk(link, data[, len])` | 发送一段流式数据（首次自动先发头）；空块会被跳过。 |
| `end_stream(link)` | 结束流式响应（分块模式补 `0\r\n\r\n`），并输出响应日志。 |
| `send_stream(link, producer)` | 用生产者回调一次完成：`bool producer(std::string& chunk)` 返回 `true` 表示还有数据。生产者抛异常视为流中断，不补结束块。 |
| `begin_stream(link)` | `send_head` 的语义化别名。 |

**便捷构造**（静态函数）：

- `Text(body, status = 200)`、`Html(...)`、`Json(...)`。
- `Status(code, message = "")`：纯状态响应。
- `Redirect(location, status = 302)`。
- `Stream(content_type = "application/octet-stream", status = 200)`：长度未知，默认分块。
- `EventStream(status = 200)`：SSE，长连接并关闭代理缓冲。
- `Download(content_type, total_size, filename = "")`：定长流式下载，`filename` 非空时输出
`Content-Disposition` 附件头。

#### HTTP::Cookie

字段：`name`、`value`、`path`、`domain`、
`expires`、`max_age`（<0 不输出）、`secure`、
`http_only`、`same_site`。
提供链式设置：`set_path` / `set_domain` / `set_max_age` /
`set_secure` / `set_http_only` / `set_same_site`，
以及 `to_string()`。

#### HTTP::Limits（解析资源上限）

**Limits 默认值**

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `max_request_line` | 8 KiB | 请求行最大字节数（超出 → 414）。 |
| `max_header_line` | 8 KiB | 单个请求头行最大字节数。 |
| `max_header_count` | 100 | 请求头最大数量（超出 → 431）。 |
| `max_header_bytes` | 64 KiB | 请求头总字节数（超出 → 431）。 |
| `max_body_bytes` | 8 MiB | 请求体最大字节数（超出 → 413）。 |

#### 工具函数与访问日志开关

- `url_decode` / `url_encode` / `to_lower` / `trim_copy`
- `base64_encode`（字节指针 + 长度，或 `std::string`）
- `sha1(data)`：返回 20 字节原始摘要（非十六进制串）
- `status_text(code)`：状态码 → 原因短语
- `http_date(t = now)`：RFC 1123 日期串
- `access_log_enabled()` / `set_access_log(bool)`：全局访问日志开关（默认开启，线程安全）
- `detail::current_request()` 等：当前线程正在处理的请求上下文（供框架内部使用）

### 7.3 Router 与 RequestFilter

#### HTTP::Router

一个 Router 对应路由表中的一条路径，可同时处理多种请求类型
（同一路径允许按请求类型注册多个 Router，例如 HTTP 与 WebSocket 各一个，互不覆盖）：

```cpp
class Router
{
public:
    virtual bool supports(RequestType type) const;              // 默认只支持 Http
    virtual void handle_request(TCP::Base_Link &link, const Header_get &header);
    virtual void handle_websocket(WebSocket &ws, const Header_get &header);
    virtual bool handle_custom(TCP::Base_Link &link, const Header_get &header); // 返回 true 表示已处理
};
```

`RequestType` 取值：`Http`、`WebSocket`、`Custom`。
需要新协议时扩展枚举并配合 `Router::supports` / `handle_custom`。

#### HTTP::RequestFilter（中间件）

```cpp
class RequestFilter
{
public:
    virtual FilterAction inspect(Header_get &request,
                                 TCP::Base_Link &link,
                                 Header_send &response) = 0;
};
```

- 返回 `FilterAction::Continue` 放行；返回 `Block` 时立即用 `response`
回应客户端并关闭连接。
- 过滤器**可以修改** `request`（规范化 url、增删头），修改会影响后续过滤器与路由匹配。
- 多个过滤器**按注册顺序**执行；任一返回 Block 即终止后续流程。
- 过滤器抛异常按“拒绝”处理（fail-closed），回应 500。
- 也可用 `Distributor::add_filter(lambda)` 直接注册函数式过滤器。

### 7.4 HTTP::Distributor（分发器）

接受连接 → 匹配路由 → 按类型分发；每个连接在独立线程中处理。

**Distributor 主要接口**

| 方法 | 说明 |
| --- | --- |
| `Distributor(TCP::Server&)` | 绑定监听服务器。 |
| `add_router(path, router)` | 注册到**默认域名表**（对任意 Host 生效）；写入该路径的**通用槽位**，不覆盖同路径的 WebSocket 处理器；同一路径重复注册时后者替换前者并告警。 |
| `add_router(host, path, router)` | 注册到域名专属表，支持精确域名与通配子域（多个通配同时命中时取后缀最长的一条）。 |
| `static std::string normalize_host(const std::string&)` | 转小写、去端口、去结尾点。 |
| `add_websocket_router(path, handler)` | 写入该路径的 **WebSocket 专用槽位**，与同路径 HTTP 处理器共存（互不覆盖）。 |
| `add_websocket_router(host, path, handler)` | 域名版。 |
| `set_not_found_router(router)` / `(host, router)` | 设置兜底处理器（按请求类型调用；默认 404）。 |
| `set_websocket_handler(handler)` | 全局兜底 WebSocket 处理器（优先级低于 `set_not_found_router` 的兜底处理器）。 |
| `set_type_classifier(fn)` | 自定义请求类型判定（默认：升级请求 → WebSocket，其余 → Http）。 |
| `set_read_timeout_ms(ms)` | 单次请求读取总超时，默认 30000；0 表示不限制（不推荐）。 |
| `set_limits(const Limits&)` | 设置解析资源上限。 |
| `set_keep_alive(bool)` | 是否启用连接复用（默认关闭）。 |
| `set_tls(ctx, handshake_timeout_ms = 10000)` | 启用 HTTPS/WSS；传 `nullptr` 关闭。 |
| `tls_enabled()` | 是否已启用 TLS。 |
| `add_filter(...)` / `clear_filters()` | 注册 / 清空请求过滤器。 |
| `start()` / `stop()` / `running()` | 启动（后台线程接受连接）/ 停止（关闭监听与所有活动连接并等待线程结束）/ 状态查询。 |

**调用顺序约束**：`add_router`、`add_filter`、`set_tls`
都应在 `start()` 之前完成。

**分发顺序**（一次请求）：

1. 按请求类型判定器得到类型（默认：WebSocket 升级请求 → `WebSocket`，其余 → `Http`）。
2. 执行请求过滤器；任一拦截则不再路由。
3. 规范化 Host：**精确域名表** → **通配子域表（后缀最长）** → **默认表**；
命中域名表后不再回退默认表。
4. 在该表内匹配路径：**精确优先**，其次**最长前缀**。
5. 按请求类型取处理器：WebSocket 请求优先用同路径的 WebSocket 专用处理器，否则用声明支持该类型的通用处理器；
该路径没有当前类型的处理器时交给兜底处理器。WebSocket 的最终回退顺序为：
路由 → `undefine_roter.websocket` → 全局 WebSocket 处理器 → 404。

访问日志里的 `route:` 字段会写明命中的是
`matched host /path`、`matched default /path`，
还是 `… has no WebSocket handler`（路径命中但类型不匹配），
可直接判断 404 是域名、路径还是请求类型导致的。

### 7.5 HTTP::WebSocket

基于 RFC 6455 的服务端实现，封装一条 TCP 连接。

- `static bool Handshake(TCP::Base_Link& link, const Header_get& request)`：
校验升级请求并回发 `101 Switching Protocols`。
- `bool valid() const`：连接是否仍打开。
- `SendText(const std::string&)` / `SendBinary(const std::vector<char>&)` /
`SendPing(payload)` / `SendPong(payload)`：发送各类帧。
- `void Close(uint16_t code = 1000, const std::string& reason = "")`：发送关闭帧并关闭底层连接。
- `bool Recv(std::string& out, bool& is_binary, int timeout_ms = 0)`：
收一条完整应用层消息（自动处理分片与 Ping/Pong），关闭/超时/出错返回 false。
- `RecvStatus RecvEx(std::string& out, bool& is_binary, int timeout_ms = 0)`：
同上，但区分 `Message` / `Timeout` / `Closed` / `Error`。
聊天类长连接服务用短超时轮询，超时后继续做广播推送。
- `Opcode`：`Continuation`、`Text`、`Binary`、`Close`、`Ping`、`Pong`。
- `link()`：取底层连接引用。

内部维护接收缓冲区与分片累积区；解析失败（超时/关闭）时**不消费**接收缓冲区，
下次可安全重试，避免半个帧被丢弃导致后续帧错位。

### 7.6 TLS（命名空间 TLS，OpenSSL 实现）

模块负责把一条已建立的 TCP 连接升级为加密连接，上层无需改动即获得 HTTPS / WSS。
底层是 `boost::asio::ssl::stream`，证书与协议版本由 OpenSSL 管理。

- `bool available() noexcept`：当前构建是否可用 TLS（链接了 OpenSSL 即为 true）。
- `struct Cert_source`：`pfx_path` + `pfx_password`，或 `cert_file` + `key_file`（PEM）。
- `struct Server_config`：`std::vector<Cert_source> certs`（第一张为默认，其余按 SNI 选择）、
`enable_tls12` / `enable_tls13`。
- `std::shared_ptr<Context> make_server_context(const Server_config& cfg, std::string& error)`：
加载证书与私钥、限制协议版本，上下文可被多条连接共享；`Context::native()` 返回
`boost::asio::ssl::context&`。

**TLS::Server_config 字段**

| 字段 | 说明 |
| --- | --- |
| `pfx_path` / `pfx_password` | PKCS#12（.pfx / .p12）证书与私钥。 |
| `cert_file` / `key_file` | PEM 证书链与私钥（OpenSSL 原生格式）。 |
| `certs`（数组） | 多域名：第一张是默认证书，其余按 ClientHello 的 SNI 自动选择。 |
| `enable_tls12` / `enable_tls13`（默认均为 true） | 协议开关；同时关闭则启动失败。 |

### 7.6.1 PFX 加密算法与 legacy provider

OpenSSL 3.x 默认只加载 `default` provider，RC2 / RC4 / DES 等老算法被移到了
`legacy` provider。Windows 的旧式导出（`certutil -exportPFX`、IIS、
旧版 CA）常用 `pbeWithSHA1And40BitRC2-CBC` 加密证书包，这种 PFX 在只有
default provider 时加载失败：

```
failed to create TLS context: certificate #1: cannot decrypt PFX: ... error:0308010C:digital envelope routines::unsupported
```

程序启动时会尽力加载 `legacy` provider（加载失败则忽略，不影响 TLS 本身），
所以**OpenSSL 自带 legacy 模块**时老式 PFX 可以直接用；本项目的 Windows
静态构建没有打包该模块，需要在导出侧解决：

- 用 AES 或 3DES 重新导出：`Export-PfxCertificate -CryptoAlgorithmOption AES256_SHA256`，
或 `openssl pkcs12 -export -certpbe AES-256-CBC -keypbe AES-256-CBC -macalg sha256`；
- 或改用 PEM：`cert_file` + `key_file`（完全绕开 PKCS#12 加密）。

加载失败时的报错会区分两种原因：`mac verify failure` 表示密码错；
`unsupported` 表示算法不受支持（即上面的情况）。

协议范围：TLS 1.2 / 1.3（禁用 SSLv2 / SSLv3、压缩与重协商，服务端优先套件）。
证书域名匹配使用 `X509_check_host`，支持 SAN 与 `*.example.com` 通配（只匹配一级）。
**不再支持** Windows 证书存储（`cert_thumbprint` / `cert_subject` / `store_name`）。
握手在 I/O 线程完成并带超时（默认 15 秒），超时或报文非法会直接关闭连接。

### 7.8 JS 文件策略

```cpp
namespace JS
{
struct File_rule
{
    std::string script;                  // 脚本匹配模式（相对脚本目录，大小写不敏感）
    std::vector<std::string> read_dirs;  // 允许读的目录（空 = 禁止读）
    std::vector<std::string> write_dirs; // 允许写的目录（空 = 禁止写）
};

struct Sql_rule
{
    std::string script;                  // 脚本匹配模式，写法同 File_rule::script
    std::vector<std::string> read_dbs;   // 允许只读打开的数据库（路径模式）
    std::vector<std::string> write_dbs;  // 允许读写的数据库（路径模式）
};

struct File_policy
{
    std::string script_dir;                        // 规则基准（绝对路径）
    std::vector<File_rule> rules;                   // 脚本级文件规则；为空 = 禁用文件功能
    std::vector<Sql_rule> sql_rules;                // 脚本级 SQL 规则；为空 = 禁用 sqlite
    std::vector<std::string> full_access_scripts;   // 完全访问脚本（规范化绝对路径，小写）
    std::size_t max_read_size = 8u * 1024u * 1024u; // 单次读取上限（0 = 不限制）
};

void set_file_rules(File_policy policy);          // 进程级，影响之后创建的 JS 上下文
File_policy get_file_policy();
}
```

`File_rule::script` 是通配模式：
`"index.js"` 精确匹配、
`"api/*.js"` 中 `*` 匹配任意字符但不跨目录、
`"api/**"` 跨目录匹配、
`"*"` 为兜底规则。
匹配优先级：精确 > 其它通配 > 兜底。目录在 `set_file_rules` 中统一规范化成绝对路径。

`Sql_rule` 与 `File_rule` 一一对应：`read_dbs` /
`write_dbs` 是数据库文件路径模式，同样支持通配；`write_dbs` 同时包含读权限。
`full_access_scripts` 中的脚本跳过全部规则检查（文件与 SQL 都是全权）。

示例 `main.cpp` 会为路由脚本、安全检测脚本与全局数据脚本一起生成规则：
前者的权限来自 `roter` / `undefine_roter` 的处理器字段，
后两者来自 `base_msg.js_security_script` / `base_msg.js_global_script`
的对象写法（字符串写法只给路径，其中全局脚本沿用旧版本的全权行为）。

### 7.9 JS 超时、Security 与 Global

```cpp
namespace JS
{
struct Timeouts

std::string global_get(const std::string &key, bool &found);   // 返回 JSON 文本

bool global_has(const std::string &key);
std::vector<std::string> global_keys();
std::string global_call(const std::string &name, const std::string &args_json,
                        std::string &error);                   // 返回 JSON 文本

// 由 base_msg.js_security_script 构造的请求过滤器：
// check(req) 返回 true/undefined 放行、false -> 403、number -> 该状态码、

std::shared_ptr<HTTP::RequestFilter> make_security_filter(const std::string &script_path,

}
```

超时由 QuickJS 的 interrupt handler 实现：脚本在截止时间后抛出
`InternalError: interrupted`，调用方按脚本异常处理。

内存上限同样由 QuickJS 提供（`JS_SetMemoryLimit`）：三个值分别作用于业务脚本、
安全检测脚本、全局数据脚本的运行时，`0` 表示不限制。
示例 `main.cpp` 在创建任何上下文之前调用 `JS::set_limits()`，
并把这三个生效值写进启动日志。

## 8. 运行时行为约定

### 8.1 线程模型

- 主线程：解析配置、启动监听、等待回车退出。
- 每个监听端口一个 `Distributor`，其 `accept_loop` 在独立线程中循环
`get_link()`。
- 每条连接一个工作线程：TLS 握手 → 请求解析 → 过滤器 → 路由 → 处理器（可能执行 JS）。
- TLS 握手在**工作线程**完成，握手失败直接丢弃连接，不阻塞 `accept`。
- 活动连接登记在 `clients_` 中，`stop()` 时统一关闭并等待线程结束。

### 8.2 连接复用（Keep-Alive）

- 需显式启用：`Distributor::set_keep_alive(true)`（示例 `main.cpp` 已启用）。
- 自动决策条件：客户端允许复用 + 已启用 Keep-Alive + 响应体可定界 →
输出 `Connection: keep-alive`，否则 `Connection: close`。
- 处理器无需手动设置 `Header_send::keep_alive`；需要强制关闭时可把
`keep_alive_auto` 置 false 并设 `keep_alive = false`。

### 8.3 响应体定界与抑制

- **一次性发送**：`body` 就绪后 `send()`，框架自动补 `Content-Length`。
- **流式发送**：首次 `send_head`/`send_chunk` 会把 `streaming` 自动置真，
避免“头里写了 Content-Length 却又追加数据”的畸形响应。
- **HEAD 请求**：不发送响应体，但 `Content-Length` 仍按 `body.size()` 计算（HEAD 语义）。
- **1xx / 204 / 304**：不发送响应体。

### 8.4 优雅关闭

发送响应后需要断开时，框架先 `Shutdown_send()` 半关闭写方向，再
`Drain()` 排空对端剩余数据，避免未读数据触发 RST 冲掉已发出的响应
（典型场景：413 / 414 / 431 错误响应）。

### 8.5 错误与状态码约定

**框架自动产生的状态码**

| 场景 | 状态码 |
| --- | --- |
| 请求畸形（请求行 / 头格式非法） | 400 |
| 读取请求超时 | 408 |
| 请求体超过 `max_body_bytes` | 413 |
| 请求行超过 `max_request_line` | 414 |
| 请求头行 / 数量 / 总字节超限 | 431 |
| 未匹配路由且无 `undefine_roter` | 404 |
| 过滤器抛异常 | 500 |
| JS 脚本抛异常或未调用 `send()` | 500 |
| WebSocket 脚本异常 | 关闭码 1011 |

## 9. 日志与运维

### 9.1 输出目标

**日志分流**

| 内容 | 控制台 | 文件 |
| --- | --- | --- |
| 普通日志（LOG / WARNING / ERROR） | 是（带颜色） | `LOG/<YYYY.MM.DD>.txt` |

| DEBUG | 是 | **不写入文件** |

控制台颜色由 `base_msg.colorful_log` 控制（默认 `true`）：
设为 `false` 后控制台只输出纯文本，不写任何 ANSI 转义序列，
适合 Windows 旧控制台、重定向到文件 / 管道、或在日志被上层采集时避免污染；
落盘文件日志本来就不含转义序列，不受此开关影响。

`LOG` 目录在日志线程启动时自动创建；时间格式为 `YYYY.MM.DD HH:MM:SS`。
日志通过**队列 + 条件变量**异步落盘，避免阻塞业务线程。

### 9.2 访问日志记录内容

- 连接建立 / 断开（含 `IP:端口`）。
- HTTP 请求（方法 / 路径 / Host / 内容类型）。
- HTTP 响应（状态码 / 字节数 / 是否复用连接）。
- WebSocket 连接建立 / 关闭。

访问日志是**全局开关**，对所有 `Distributor` 实例生效且线程安全：
`HTTP::set_access_log(false)` 关闭，`HTTP::access_log_enabled()` 查询当前状态（默认开启）。

## 10. 安全实践

### 10.1 已有防护

- **解析上限**：请求行、请求头行、头数量、头总字节、请求体均有上限。
- **总超时**：整个请求的读取有统一超时，防 Slowloris 慢速攻击（默认 30000 ms）。
- **有界读取**：`Read_until` 返回 `Overflow` 即建议断开。
- **文件沙箱**：脚本路径按相对脚本目录解释，拒绝 `..` 与绝对路径，
消解符号链接后再校验，读 / 写方向独立；除非该脚本显式开启 `js_full_access`。
- **SQL 沙箱**：`Sqlite` 只在配置了 `js_sql_*_rule` 时安装，
数据库路径同样消解 `..` 与符号链接后与允许列表比对，读写方向独立。
- **脚本隔离**：每次请求新建运行时，脚本间无共享全局状态。
- **过滤器 fail-closed**：过滤器异常按拒绝处理，不会误放行。
- **脚本内存上限**：业务 / 安全 / 全局脚本各有独立的可配置上限（默认 64 / 64 / 128 MiB），
超出时该次脚本以异常结束，按各入口的 fail-closed 规则处理。
- **静默断开**：安全脚本返回 `-1`（或 `{ close: true }`）时直接关闭连接，
不向可疑客户端发送任何响应报文。
- **TLS 1.2 / 1.3**：由 OpenSSL 实现，证书来自 PFX 或 PEM 文件；
不支持 Windows 证书存储（`cert_thumbprint` / `cert_subject` 已移除）。

### 10.2 部署建议

1. **不要用高权限账户运行**：脚本可以读写被允许的目录，权限越小题越小。
2. **最小授权**：`js_read_rule` / `js_write_rule` 只给必需的目录，
不要写成脚本目录本身；`js_sql_read_rule` / `js_sql_write_rule` 同理。
3. **慎用 js_full_access**：它等价于把进程账户的整个文件系统与
任意 sqlite 库交给该脚本，只对完全可信的运维 / 工具脚本开启，并在代码评审中重点检查。
4. **生产环境开启 HTTPS**：给出 `HTTPS_port` + `pfx_path`，
并考虑关闭明文端口。
5. **启用访问日志**，定期归档 `LOG/access.*.txt`。
6. **收紧 Limits**：按业务实际请求大小下调 `max_body_bytes` 等上限。
7. **用过滤器做前置拦截**：IP 黑名单、UA 校验、路径白名单、简单限流。
8. **敏感信息不要写日志**：脚本里的 `log()` 会落盘。
9. **脚本视为可信代码**：脚本拥有被授予的文件权限，不要允许上传或动态生成脚本。

### 10.3 Cookie 安全属性

- `httpOnly = true`：禁止前端脚本读取，降低 XSS 窃取风险。
- `secure = true`：仅 HTTPS 传输。
- `sameSite = "Strict"` 或 `"Lax"`：缓解 CSRF。
- 删除 Cookie 用 `Header_send::delete_cookie(name, path)`。

## 11. 常见问题（FAQ）

- **启动报 “no listen port configured”**
  `base_msg.HTTP_port` 与 `base_msg.HTTPS_port` 都是 0 或缺失。
至少配置一个有效端口。
- **设置了 HTTPS_port 但没有 HTTPS**
  日志会提示 `pfx_path is empty`。补上 `pfx_path`（相对路径以配置文件所在目录为基准），
并确认 `TLS::available()` 为真。
- **多个域名共用一个 HTTPS 端口，浏览器提示“证书域名不符”**
  一张 PFX 只覆盖它 CN / SAN 里的域名。请用 `base_msg.certificates`
为每个域名各配一张证书（第一张是默认证书），程序会按客户端 SNI 自动选择；
启动日志会告警“route host ... is not covered by any configured certificate”，
按提示补齐即可。若域名有共同后缀，也可以用一张 `*.example.com` 通配证书。
- **本机能用 https，外网访问超时（HTTP 正常）**
  Hhttp 只负责在端口上监听，外网能否连上由服务器网络策略决定。请依次检查：
① 云主机安全组放行入站 TCP 443（腾讯云 / 阿里云等默认只放行常见端口，
需在控制台的安全组入站规则中单独添加 443）；
② Windows Defender 防火墙放行 `Hhttp.exe` 或 TCP 443 入站；
③ 路由器 / NAT 上把 443 映射到本机；
④ 在服务器本机执行 `curl -k https://127.0.0.1:443/` 验证服务端 TLS 是否正常。
若本机也失败，日志中的 `TLS handshake failed: <ip> (<原因>)`
与连接日志里的 `protocol: TLS 1.3 / TLS 1.2` 可直接定位是证书、协议还是端口问题。
- **请求返回 404，但路由已配置**
  按顺序检查：① 域名是否匹配（浏览器请求的 Host 与路由键前半段要一致；
多个通配子域同时命中时取**后缀最长**的那张表，例如 `*.wild.test` 优先于 `*.test`）；
② 路径是否精确 / 前缀匹配（结尾要写 `/`）；
③ **请求类型**是否匹配（只配了 `websocket` 的路由不处理普通 HTTP 请求，
反之亦然；类型不匹配会交给 `undefine_roter` 里对应类型的处理器）；
④ 该路由是否写了 `js_path`（没写会被忽略并打告警）；
⑤ 域名专属表命中后不会再回退默认表，兜底处理器需按域名安装（`main.cpp` 已处理）。
访问日志的 `route:` 字段会直接写出是否命中、命中的哪张表哪条路径，
以及“路径命中但没有该类型的处理器”，可先看它定位。
- **脚本改了不生效**
  每次请求都会重新加载脚本文件，正常情况下改完立即生效。若仍不生效，
确认 `--dir` 与配置中的 `js_path` 是否指向同一文件
（启动日志会打印每条路由解析后的绝对路径）。
- **脚本报 500，页面显示 “JS script error”**
  日志里有完整异常堆栈（含脚本路径与对端地址）。常见原因：未调用 `res.send()`、
访问了未定义变量、JSON 序列化失败（含循环引用）。
- **File.read 抛异常 / 被拒绝**
  该脚本没有读权限，或路径越界。检查 `js_read_rule` 是否包含目标目录，
路径是否写成相对脚本目录的形式，是否用了 `..` 或绝对路径。
- **WebSocket 脚本里 recv 一直返回 undefined**
  表示超时（连接仍有效），这是正常现象，用于在等待消息的同时做推送。
返回 `null` 才是连接关闭。若要无限等待，调用 `ws.recv()` 或不传参数（0）。
- **下载大文件时内存暴涨**
  不要用 `File.read()` 再 `res.binary()`。用 `res.file(path)`
（定长流式，64 KiB 分块），或 `res.beginStream()` + `res.chunk()` + `res.endStream()`。
- **想只读大文件的一段**
  用 `File.read(path, start, end)` 或 `File.readText(path, start, end)`，
区间为 `[start, end)`、单位字节，负数从末尾倒数。上限 `file_max_size` 只校验实际读取的区间，
整文件超限也能分块读。
- **怎样让安全脚本直接断开连接**
  `check(req)` 返回 `-1`（或 `{ close: true }`）：框架不写状态行 / 响应头 / 正文，
直接关闭 socket，日志记为 `Request dropped`。返回 `false` 或数字才是“先发响应再断开”。
- **脚本内存上限怎么调**
  写 `base_msg.js_memory_limit` / `js_security_memory_limit` /
`js_global_memory_limit`（字节，`0` 表示不限制），或用 `--js-memory-limit`
等命令行参数覆盖；启动日志会打印三个生效值。
- **控制台出现 `ESC[32m` 之类的可见乱码**
  终端不支持 ANSI 转义序列：把 `base_msg.colorful_log` 设为 `false`
（默认 `true`），日志改为纯文本；文件日志始终不带转义序列，不受影响。
- **启动报 cannot decrypt PFX / digital envelope routines::unsupported**
  PFX 用了 OpenSSL 3 默认不启用的旧加密算法（RC2 / RC4 / DES，Windows 旧式导出常见）。
用 AES 或 3DES 重新导出（`Export-PfxCertificate -CryptoAlgorithmOption AES256_SHA256`），
或改用 PEM（`cert_file` / `key_file`）。详见 7.6.1。
- **日志目录在哪**
  进程当前工作目录下的 `LOG/`，首次写日志时自动创建；
主日志 `LOG/<日期>.txt`，访问日志 `LOG/access.<日期>.txt`。
- **能否跨平台运行**
  可以。传输层是 Boost.Asio（Windows IOCP / Linux epoll），TLS 是 OpenSSL；
Windows x64 与 Linux aarch64 均已通过全部回归用例，macOS 尚未实机验证。详见第 13 章。

## 12. 已知限制

- **仅支持 HTTP/1.1**：未实现 HTTP/2、HTTP/3（无多路复用、HPACK、QUIC）。
- **平台支持**：Windows x64 与 Linux aarch64 已验证；macOS 代码就绪但未实机验证；
Windows 证书存储（`cert_thumbprint` / `cert_subject`）已随 SChannel 一起移除。
- **监听地址固定**：命令行只监听 `0.0.0.0`；`TCP::Server` 支持传入绑定地址，
但尚未做成配置项。
- **每连接一线程**：连接数很高时线程开销明显，不适合十万级并发；
如需更高并发需改造为 IO 多路复用 + 线程池。
- **无内置压缩**：未实现 gzip / brotli 协商，需自行在脚本或前置代理处理。
- **无内置静态目录服务**：静态文件通过 `res.file()` 逐个提供。
- **无内置会话 / 模板 / 路由参数**：`/user/:id` 这类参数化路由需自行解析
（可用前缀匹配 + `req.url()` 拆分）。
- **策略为进程级**：同一脚本只能有一条文件规则与一条 SQL 规则，一个进程内共享；
`js_full_access` 按脚本路径生效。
- **QuickJS 为外部依赖**：需自行提供头文件与库（当前使用 2026-06-04 版本），工程内不含其源码。
- **脚本无持久化状态**：每次请求新建上下文，跨请求数据需借助文件、Cookie 或外部存储。

### 13.3 Windows 构建与产物

```powershell
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release `
  -DHHTTP_BOOST_DIR=A:/libs/boost_1_92_0 `
  -DHHTTP_OPENSSL_DIR=A:/libs/openssl `
  -DHHTTP_QUICKJS_DIR=A:/libs/quickjs `
  -DHHTTP_SQLITE3_DIR=A:/libs/sqlite3
cmake --build build
```

- 产物 `build/Hhttp.exe`：**Release**（`-O2 -DNDEBUG`），约 **17.2 MiB**。
- 体积主要来自**全静态链接**：OpenSSL（`libcrypto.a` 9.3 MB + `libssl.a` 1.6 MB）、
  QuickJS（6.8 MB）、SQLite（1.4 MB），加上 `-static` 链入的 libstdc++ / libgcc / winpthread；
  对外只依赖系统 DLL，拷一个 exe 即可运行。
- 其中约 **8 MB 是调试信息**（预编译静态库自带 `.debug_*` 段）。发布前 strip 可减半：

```bash
strip -s build/Hhttp.exe        # 17.2 MiB -> 9.3 MiB，功能不变
```

- **MSVC**：用 `cmake -S . -B build -G "Visual Studio 17 2022" -A x64` 生成工程，
  但需要 MSVC 编译的 QuickJS / SQLite3 / OpenSSL；MinGW 的 `.a` 不能直接用于 MSVC。
  也可以用 vcpkg 安装 OpenSSL 与 SQLite3，再自行编译 QuickJS。

### 13.4 Linux 构建与部署

Linux 上依赖一般由包管理器提供：

```bash
# Debian / Ubuntu 示例
sudo apt install build-essential cmake ninja-build libboost-dev libssl-dev libsqlite3-dev
# QuickJS 需自行编译(见 13.2)，假设放在 /opt/quickjs
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
    -DHHTTP_QUICKJS_DIR=/opt/quickjs
cmake --build build -j
```

不指定 `HHTTP_*_DIR` 时 CMake 会走 `find_package` / `find_path` 回退，
适合依赖已装在系统默认路径的机器。

推荐的生产部署布局（与源码仓库解耦，只需要可执行文件 + 配置 + 脚本）：

```text

├─ Hhttp                可执行文件
├─ config.json          配置
├─ scripts/             业务脚本
├─ certs/               PFX / PEM 证书
└─ LOG/                 日志(运行时创建)
```

启动：

```bash
cd /opt/hhttp && ./Hhttp --config config.json --dir scripts
```

### 13.6 跨平台适配中修复的问题

- **js_full_access 在 POSIX 下失效**：脚本绝对路径规范化时把开头的 `/` 删掉了，
POSIX 下退化成相对路径、又被拼上脚本目录，导致完全访问脚本匹配不上（表现为
`Global.call` 里的 `File.exists` 被拒绝）。已新增 `normalize_abs_text()` 保留根路径，
Windows 与 Linux 两侧回归均重新验证。
- **QuickJS 源码根不能直接当 include 路径**：源码里的 `VERSION` 文件在大小写不敏感的挂载上
会劫持 `<version>` 头，导致大量标准库符号“未定义”的假错误；只导出 `quickjs.h` 即可。
- **Windows 证书存储不再支持**：`cert_thumbprint` / `cert_subject` 随 SChannel 一起移除，
改用 `pfx_path` 或 `cert_file` + `key_file`。

| 204 | No Content | 无响应体。 |
| 301 / 302 / 307 | Moved Permanently / Found / Temporary Redirect | `Header_send::Redirect`。 |
| 304 | Not Modified | 缓存协商，无响应体。 |
| 400 | Bad Request | 请求畸形。 |
| 403 | Forbidden | 过滤器拦截。 |
| 404 | Not Found | 未匹配路由 / 脚本未配置。 |
| 408 | Request Timeout | 读取请求超时。 |
| 413 | Content Too Large | 请求体超限。 |
| 414 | URI Too Long | 请求行超限。 |
| 429 | Too Many Requests | 限流（自行实现）。 |
| 431 | Request Header Fields Too Large | 请求头超限。 |
| 500 | Internal Server Error | 脚本异常 / 过滤器异常。 |
| 502 / 503 | Bad Gateway / Service Unavailable | 上游或维护状态（自行实现）。 |

### 附录 C：术语表

- **Router**
  路由处理器：一个 Router 对应路由表中的一条路径，负责处理到达该路径的请求。
- **Distributor**
  分发器：接受连接、执行过滤器、匹配路由，再按请求类型分发给对应处理入口。
- **RequestFilter**
  请求过滤器（中间件）：路由匹配之前执行，可只读检查、拦截并回应、或修改请求后放行。
- **Limits**
  请求解析资源上限，用于防御 Slowloris 与超大报文等 DoS 攻击。
- **流式响应**
  响应体长度未知或边生成边发送（SSE、大文件下载、实时日志），用 chunked 或关闭连接定界。
- **脚本目录（script_dir）**
  配置里 `js_path` 与文件读写规则的基准目录，默认 `scripts`，可用 `--dir` 覆盖。
- **路由键**
  配置中 `"域名/路径"` 形式的字符串，决定该处理器对哪些 Host 与路径生效。
- **兜底处理器（undefine_roter）**
  没有匹配到可处理该请求类型的路由时使用的处理器（`http` / `websocket` 分别生效）；未配置时框架返回 404。
